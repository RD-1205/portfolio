Financial Filings Data Platform Ingests public company filings, normalises them, and lets you query the result as of any past date Python FastAPI SQLite HTMX pytest 285k filings parsed · two wrong numbers found

A stock screener built on public regulatory filings. It pulls raw filing data, normalises it into something queryable, computes the usual financial ratios, and serves it as a website. Ingestion, schema, query engine and interface are all mine.

The idea it's built around is small but it changes the architecture. Every free screener I looked at rebuilds history from today's data. So when you ask one "what would this filter have returned in 2019", it answers using figures that were revised years later, and companies that hadn't listed yet. The results look better than reality and you can't patch it afterwards, because the information needed is already gone. I keep the filing date on every single datapoint, which means a historical query returns only what was genuinely on file that day.

The part I'd point to is a bug I nearly shipped. Trailing-twelve-month revenue is supposed to be the last four quarters added together, so that's what I did, and the numbers looked completely reasonable. They were about 7% too low. US companies file three quarterly reports and one annual report, which means the fourth quarter is never published on its own — summing "the last four rows" silently picks up a quarter from the previous year instead. Nothing crashes. Every margin and valuation ratio on the site is just quietly wrong.

The fix took a few lines. What took longer was deciding what to test. Asserting the code doesn't raise an exception would have caught nothing here, so the tests assert that the numbers reconcile — that four quarters add up to the year they belong to. Several other tests are the same shape: a company with negative equity must not be able to appear in a "highest return on equity" ranking, because dividing by a negative number produces a spectacular result for a company that is technically insolvent.

The other genuinely hard part is that the source data has no consistent vocabulary. Filers pick from roughly 14,000 possible field names, and two companies in the same industry routinely pick different ones for the same concept. Extracting a single field name silently returns nothing for a large share of the market, so there's a resolution layer that maps candidate names onto one schema and records which one it used, so any figure can be traced back to the filing it came from.

I built it first against a synthetic corpus — six fake companies, each designed to break one specific thing — then ran it on real filings. 285,000 facts across 65 companies. The field-name mapping resolved revenue, net income, total assets and equity for 98% of them. Apple's 2021 revenue came out at $365.82B against $365.82B in the actual filing.

Real data also surfaced a second wrong number, and this one I would not have found any other way. Apple's earnings-per-share history read 8.31, 9.21, 2.98, 2.97 — a fourfold drop between two years where nothing happened. The cause is a stock split. When a company splits its stock it retroactively restates its historical per-share figures, but only for the years still shown as comparatives in its next report. Older years keep the original numbers. My "use the most recently published value" rule — correct for revenue — was silently stitching two different bases into one series.

The fix fell out of a decision I'd made much earlier for a different reason. Because I keep every published version of every figure rather than overwriting, the same year restated across two reports differs by exactly the split ratio. That let me recover 27 split events across 11 companies — Apple 7:1 and 4:1, Amazon 20:1, Nvidia 10:1, Tesla 3:1 — from data I already had, with no external data source. Keeping history instead of overwriting it paid for itself twice.

Job Market Salary Predictor Salary prediction from job postings, built end to end Python PyTorch scikit-learn FastAPI PostgreSQL 79.8% accuracy vs a 47.8% baseline

Predicts salaries from job postings. I built the whole thing: a FastAPI backend, PostgreSQL for storage, and a Streamlit interface so people who don't write code could query it without going through me.

The part I'd point to is the rebuild. My first model got 54.6%, which sounds fine until you check it against a 47.8% baseline. I reworked it into a two-stage model, TF-IDF feeding into gradient boosting, and got it to 79.8%.

Along the way I caught an easy 85% that turned out to be the model reading salaries straight out of the posting text, a leak, not a real signal, so I identified it and rejected it. To make sure the real number held up, I validated on employers the model had never seen, which came in at 71.4%. I documented the whole process for both technical and non-technical readers.
